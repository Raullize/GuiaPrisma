# Migrations: Gerenciando o Banco de Dados

## O que são Migrations?

Migrations são scripts que descrevem mudanças incrementais no schema do banco de dados. Elas permitem:
- **Versionamento** do schema do banco
- **Colaboração** em equipe com mudanças sincronizadas
- **Deploy** seguro em produção
- **Rollback** para versões anteriores

## Como Funcionam no Prisma

O Prisma gera migrations automaticamente comparando:
1. Estado atual do banco de dados
2. Schema definido em `schema.prisma`
3. Histórico de migrations anteriores

## Estrutura de Migrations

### Diretório de Migrations

```
prisma/
├── schema.prisma
└── migrations/
    ├── migration_lock.toml
    ├── 20231201120000_init/
    │   └── migration.sql
    ├── 20231202130000_add_user_table/
    │   └── migration.sql
    └── 20231203140000_add_posts/
        └── migration.sql
```

### Arquivo migration.sql

```sql
-- CreateTable
CREATE TABLE "User" (
    "id" SERIAL NOT NULL,
    "email" TEXT NOT NULL,
    "name" TEXT,
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "User_pkey" PRIMARY KEY ("id")
);

-- CreateIndex
CREATE UNIQUE INDEX "User_email_key" ON "User"("email");
```

### migration_lock.toml

```toml
# Please do not edit this file manually
# It should be added in your version-control system (i.e. Git)
provider = "postgresql"
```

## Comandos de Migration

### Criar Nova Migration

```bash
# Criar migration com nome descritivo
npx prisma migrate dev --name add_user_table
npx prisma migrate dev --name add_post_model
npx prisma migrate dev --name update_user_fields
```

### Aplicar Migrations

```bash
# Desenvolvimento (cria e aplica)
npx prisma migrate dev

# Produção (apenas aplica)
npx prisma migrate deploy
```

### Verificar Status

```bash
# Ver status das migrations
npx prisma migrate status

# Output exemplo:
Database schema is up to date!

The following migrations have not yet been applied:
20231203140000_add_posts
```

## Workflow de Development

### 1. Modificar Schema

```prisma
// Antes
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
}

// Depois
model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String?  // Campo adicionado
  createdAt DateTime @default(now()) // Campo adicionado
}
```

### 2. Gerar Migration

```bash
npx prisma migrate dev --name add_user_name_and_created_at
```

### 3. Revisar Migration Gerada

```sql
-- AlterTable
ALTER TABLE "User" ADD COLUMN "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
ADD COLUMN "name" TEXT;
```

### 4. Aplicar e Testar

A migration é aplicada automaticamente e o Prisma Client é regenerado.

## Tipos de Mudanças

### Mudanças Seguras (Não Destrutivas)

```prisma
// Adicionar campo opcional
model User {
  id       Int     @id @default(autoincrement())
  email    String  @unique
  name     String? // ✅ Seguro
  bio      String? // ✅ Seguro
}

// Adicionar índice
model Post {
  id       Int    @id @default(autoincrement())
  title    String
  authorId Int
  
  @@index([authorId]) // ✅ Seguro
}

// Adicionar nova tabela
model Category {
  id   Int    @id @default(autoincrement())
  name String @unique
} // ✅ Seguro
```

### Mudanças Destrutivas (Cuidado!)

```prisma
// Remover campo
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  // name String? // ❌ Campo removido - dados perdidos!
}

// Alterar tipo de campo
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  age   String // ❌ Era Int, agora String - pode falhar!
}

// Tornar campo obrigatório
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  name  String // ❌ Era opcional, agora obrigatório!
}
```

## Migrations Customizadas

### Quando Customizar

- Migração de dados complexa
- Mudanças que requerem lógica especial
- Transformações de dados
- Operações que o Prisma não consegue gerar automaticamente

### Processo de Customização

1. **Gerar migration vazia:**

```bash
npx prisma migrate dev --create-only --name custom_data_migration
```

2. **Editar arquivo SQL:**

```sql
-- Migration gerada automaticamente
ALTER TABLE "User" ADD COLUMN "fullName" TEXT;

-- Customização manual
UPDATE "User" SET "fullName" = CONCAT("firstName", ' ', "lastName") 
WHERE "firstName" IS NOT NULL AND "lastName" IS NOT NULL;

-- Remover campos antigos
ALTER TABLE "User" DROP COLUMN "firstName";
ALTER TABLE "User" DROP COLUMN "lastName";
```

3. **Aplicar migration:**

```bash
npx prisma migrate dev
```

## Migrations em Produção

### Estratégia de Deploy

```bash
# 1. Backup do banco
pg_dump mydb > backup_$(date +%Y%m%d_%H%M%S).sql

# 2. Aplicar migrations
npx prisma migrate deploy

# 3. Verificar status
npx prisma migrate status
```

### Deploy Automatizado

```yaml
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      
      - name: Setup Node.js
        uses: actions/setup-node@v2
        with:
          node-version: '18'
          
      - name: Install dependencies
        run: npm ci
        
      - name: Run migrations
        run: npx prisma migrate deploy
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

## Resolução de Problemas

### Migration Falhou

```bash
# Ver status detalhado
npx prisma migrate status

# Marcar como aplicada (se aplicou manualmente)
npx prisma migrate resolve --applied 20231203140000_failed_migration

# Marcar como falhada (para tentar novamente)
npx prisma migrate resolve --rolled-back 20231203140000_failed_migration
```

### Schema Fora de Sincronia

```bash
# Resetar desenvolvimento (CUIDADO: perde dados!)
npx prisma migrate reset

# Ou fazer baseline em produção
npx prisma migrate resolve --applied 20231203140000_baseline
```

### Conflitos de Migration

```bash
# Quando duas pessoas criam migrations simultaneamente
# 1. Fazer pull das mudanças
git pull origin main

# 2. Resetar banco local
npx prisma migrate reset

# 3. Aplicar todas as migrations
npx prisma migrate dev
```

## Boas Práticas

### 1. Nomenclatura

```bash
# ✅ Bom: descritivo e claro
npx prisma migrate dev --name add_user_profile_table
npx prisma migrate dev --name update_post_status_enum
npx prisma migrate dev --name fix_user_email_constraint

# ❌ Ruim: vago ou sem contexto
npx prisma migrate dev --name update
npx prisma migrate dev --name fix
npx prisma migrate dev --name changes
```

### 2. Mudanças Incrementais

```bash
# ✅ Bom: uma mudança por migration
npx prisma migrate dev --name add_user_avatar_field
npx prisma migrate dev --name add_post_category_relation

# ❌ Ruim: muitas mudanças juntas
npx prisma migrate dev --name add_multiple_features
```

### 3. Teste Antes do Deploy

```bash
# Testar migration em ambiente de staging
DATABASE_URL="postgresql://staging_url" npx prisma migrate deploy

# Verificar se aplicação funciona
npm test

# Só então aplicar em produção
DATABASE_URL="postgresql://prod_url" npx prisma migrate deploy
```

### 4. Backup Antes de Mudanças Destrutivas

```bash
# Sempre fazer backup antes de:
# - Remover campos
# - Alterar tipos
# - Remover tabelas

pg_dump $DATABASE_URL > backup_before_migration.sql
npx prisma migrate deploy
```

## Estratégias Avançadas

### Blue-Green Deployment

1. **Mudanças compatíveis com versão anterior**
2. **Deploy da aplicação nova**
3. **Aplicar migrations destrutivas**
4. **Remover código de compatibilidade**

### Zero-Downtime Migrations

```sql
-- Fase 1: Adicionar nova coluna
ALTER TABLE "User" ADD COLUMN "new_email" TEXT;

-- Fase 2: Migrar dados (em background)
UPDATE "User" SET "new_email" = "email" WHERE "new_email" IS NULL;

-- Fase 3: Adicionar constraint
ALTER TABLE "User" ALTER COLUMN "new_email" SET NOT NULL;
ALTER TABLE "User" ADD CONSTRAINT "User_new_email_key" UNIQUE ("new_email");

-- Fase 4: Remover coluna antiga (próxima release)
ALTER TABLE "User" DROP COLUMN "email";
ALTER TABLE "User" RENAME COLUMN "new_email" TO "email";
```

### Rollback Strategy

```bash
# Preparar migration de rollback
# rollback_20231203140000.sql
ALTER TABLE "User" DROP COLUMN "new_field";
DROP INDEX "User_new_field_idx";

# Aplicar rollback se necessário
psql $DATABASE_URL < rollback_20231203140000.sql
```
